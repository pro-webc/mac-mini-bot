# AI ワークフロー進化ロードマップ

## このドキュメントの目的

mac-mini-bot を**半 AI ワークフロー**から**自律型 AI ワークフロー**へ進化させるための全体計画を定義する。各フェーズの目的・成果物・依存関係を明確にし、実装の判断基準を提供する。

---

## 現在地と目指す姿

```
現在（半 AI）                          目標（自律 AI）
┌─────────────────┐                  ┌─────────────────┐
│ 人間 + Cursor    │  ──────────→    │ AI 評価・改善層   │
│ ・品質レビュー    │                  │ ・自動スコアリング │
│ ・プロンプト改善  │                  │ ・改善提案生成     │
│ ・障害判断       │                  │ ・A/B 実験管理     │
│ ・再開操作       │                  │ ・自律リトライ     │
└────────┬────────┘                  └────────┬────────┘
         │                                    │
         ▼                                    ▼
┌─────────────────┐                  ┌─────────────────┐
│ mac-mini-bot     │  ──────────→    │ mac-mini-bot     │
│ （変更なし）      │                  │ + 評価パイプライン │
└─────────────────┘                  │ + 可観測性基盤    │
                                     └─────────────────┘
```

**核心**: オーケストレーション層の判断を人間から AI に移転する。実行エンジンは拡張するが、既存の 5 フェーズ構造は維持する。

---

## フェーズ構成

### Phase A: 自動スコアリング基盤

**目的**: 生成サイトの品質を定量的に評価できるようにする

| 項目 | 内容 |
|------|------|
| **成果物** | 評価モジュール (`modules/evaluation/`)、スコア記録 (`output/<record>/evaluation/`) |
| **前提条件** | なし（既存の `output/` トレースがそのまま使える） |
| **完了条件** | 全案件に対してスコアが自動計算され、`evaluation/scores.json` に保存される |
| **詳細設計** | [AUTO_SCORING.md](./AUTO_SCORING.md) |

**評価軸:**

| 軸 | 評価方法 | 自動化レベル |
|----|---------|------------|
| 技術品質 | ビルド成功・Lint・アクセシビリティ | 完全自動 |
| 構造適合 | ページ数・セクション構成・CTA 配置 | 完全自動 |
| デザイン品質 | スクリーンショット → マルチモーダル LLM 評価 | LLM 依存 |
| コンテンツ品質 | ヒアリング反映度・文章品質 | LLM 依存 |
| ヒアリング忠実度 | 要件 vs 成果物のギャップ分析 | LLM 依存 |

---

### Phase B: フィードバックループ

**目的**: 評価結果からプロンプト改善を自動提案・検証する

| 項目 | 内容 |
|------|------|
| **成果物** | 改善提案モジュール、プロンプトバージョニング、A/B 比較基盤 |
| **前提条件** | Phase A（スコアがないと改善の効果が測定できない） |
| **完了条件** | 低スコア案件から改善提案が生成され、A/B 比較でスコア向上が確認できる |
| **詳細設計** | [FEEDBACK_LOOP.md](./FEEDBACK_LOOP.md) |

**サイクル:**

```
スコア低下検出 → 原因ステップ特定 → 改善案生成 → A/B 実行 → スコア比較 → 採用/棄却
     ↑                                                                    │
     └────────────────────────────────────────────────────────────────────┘
```

---

### Phase C: オーケストレーション強化

**目的**: 障害回復とリトライを自動化する

| 項目 | 内容 |
|------|------|
| **成果物** | ステップ単位リトライ、品質不足時の自動リラン、チェックポイント汎用化 |
| **前提条件** | Phase A（品質不足の判定にスコアが必要） |
| **完了条件** | Phase 2 の特定ステップのみ再実行でき、スコア閾値未満で自動リトライが走る |

**拡張対象:**

| 現在の機能 | 拡張後 |
|-----------|--------|
| scripts による手動再開 | 任意のステップから再開可能 |
| Phase 4 の `npm run build` リトライ | Phase 2 の LLM ステップ単位リトライ |
| 例外で停止 → 手動復旧 | スコア閾値未満 → 自動リトライ（上限付き） |

---

### Phase D: 可観測性

**目的**: パイプラインの状態を常時把握し、異常を早期検知する

| 項目 | 内容 |
|------|------|
| **成果物** | 構造化ログ、ダッシュボード、アラート通知 |
| **前提条件** | Phase A（スコアデータがダッシュボードの主要指標） |
| **完了条件** | 成功率・平均スコア・エラー率がリアルタイムで確認でき、異常時に通知が飛ぶ |
| **詳細設計** | [OBSERVABILITY.md](./OBSERVABILITY.md) |

---

### Phase E: 知識蓄積と活用

**目的**: 成功事例を構造化し、新案件の生成品質を底上げする

| 項目 | 内容 |
|------|------|
| **成果物** | 成功パターン DB、業種分類、Few-shot 自動選択 |
| **前提条件** | Phase A + Phase B（十分な評価データの蓄積が必要） |
| **完了条件** | 類似案件の Few-shot 注入でスコアが統計的に向上する |

---

## 依存関係

```
Phase A: 自動スコアリング ─────┬──→ Phase B: フィードバックループ
   （基盤・最優先）            │
                              ├──→ Phase C: オーケストレーション強化
                              │
                              ├──→ Phase D: 可観測性
                              │
                              └──→ Phase E: 知識蓄積（B も前提）
```

Phase A が全ての起点。ここが完成すれば B〜D は並行して進められる。

---

## 設計原則

### 1. 既存構造を壊さない

5 フェーズのパイプライン構造と `BRANCH_REGISTRY` による分岐は維持する。評価・改善は**パイプラインの外側に追加する**。

```
既存 Phase 1-5 → [新] Phase 6: 評価 → [新] Phase 7: 改善提案
```

### 2. 記録ファースト

新機能も `output/<record>/` 配下に構造化して記録する。追跡できないものは改善できない。

```
output/<record>/
├── llm_steps/          ← 既存（変更なし）
├── llm_raw_output/     ← 既存（変更なし）
├── evaluation/         ← 新規: スコア・スクリーンショット・評価詳細
└── improvement/        ← 新規: 改善提案・A/B 結果
```

### 3. 段階的に人間を外す

各フェーズで「人間承認ゲート」を設け、信頼度が上がったら段階的に外す。

| 段階 | 人間の関与 |
|------|----------|
| **Stage 1** | AI が提案 → 人間が承認 → 実行 |
| **Stage 2** | AI が実行 → 人間がレビュー（事後） |
| **Stage 3** | AI が自律実行（異常時のみ人間通知） |

### 4. YAGNI を守る

[AI_WORKFLOW_ARCHITECTURE.md](../system-rules/AI_WORKFLOW_ARCHITECTURE.md) の方針を継承。宣言的ワークフロー定義やプラグインアーキテクチャは、各フェーズの要件が具体化してから導入する。
