## 1. 技術スタック（全工程共通）

- **Next.js (App Router)**, React, **Tailwind CSS**
- セクション単位でコンポーネント化（1 セクション = 1 コンポーネント）
- CSS `@import`（Google Fonts 等）は globals.css の**最上部**（`:root` / `@theme` より前）。違反はビルドエラー

## 2. 情報設計（step 2〜3）

### ページ構成

| プラン | ページ数 | 特記 |
|--------|---------|------|
| BASIC LP | 1（LP） | ヘッダー/フッター禁止。法務はモーダル等で表示 |
| BASIC CP | 1 | サービス 4 つ以上ならタブ表示。沿革セクション禁止 |
| STANDARD | 6 固定 | TOP は下層への目次。会社概要・お問い合わせは独立ページ |
| ADVANCE | 12 固定 | ページ数が多い前提でドロップダウンナビ |

### 共通の構成ルール

- **プライバシーポリシーに独立 `page.tsx` を作らない** — 契約ページ数に含めず、既存ページ上で Dialog/Sheet/Drawer 等で表示
- **対応エリアの画像・イラスト禁止** — 所在地は Google Maps 埋め込み
- 同一ページ内遷移ボタン不可（STANDARD/ADVANCE）
- 下層ページは LP 相当の情報ブロック（料金・実績・FAQ 等）を欠かさない
- LP: 中間オファー 2 箇所以上、FAQ・お問い合わせ・会社概要は各 1 独立セクション
- LP: 実店舗なら Where 必須（会社概要と統合不可）、個人運営なら Who 必須

## 3. コンテンツライティング（step 3〜4）

### 文量の下限

| 対象 | 最低文字数 | 正本 |
|------|-----------|------|
| TOP ページ（STANDARD/ADVANCE） | 2,000 字以上 | `step_3_1.txt` |
| サービス下層ページ | 1,500 字以上 | `step_3_2.txt` |
| 会社概要ページ | 1,000 字以上 | `step_3_3.txt` |
| お問い合わせページ | 800 字以上 | `step_3_4.txt` |
| その他ページ | 800 字以上/ページ | `step_3_5.txt` |
| BASIC CP（1P 全体） | 2,500 字以上 | `step_3.txt` |

### セクション薄化禁止

- 見出し＋キャッチ 1 行だけで終えない
- 主要ブロックにはリード 1 文（誰の・何が解決するか）＋根拠・条件・手順・比較・事例型の具体を必ず載せる
- 箇条書きの項目を単語 1 つで終えない
- 「詳細はお問い合わせ」だけで中身を空にしない

### コンテンツの信頼性

- ヒアリング・仕様に**ない具体数値や実在固有名の創作は禁止**
- 不足時は「要ヒアリング」「プレースホルダ」として後工程で差し替え可能な文言に留める
- 法的・医療等の高リスク表現: 断定的効果表現や誇大広告を避ける

### ヒーロー（LP）

- キャッチ **15 字以内**
- サブはスマホ 2 行＋屋号必須
- 強み 3 つ（バッジ想定）
- ビジュアル必須

### FAQ

- 各回答は結論＋補足で**原則 2 文以上**（Yes/No 一言完結禁止）
- 業種で想定される不安・障壁・手続きをできる限り覆う
- STANDARD/ADVANCE サービス下層は最低 5 問

### フォーム

- プルダウン（対象）・名前・メール必須、電話、内容
- フォーム上に「2 日以内に連絡」文言必須
- 各入力に視覚的に紐づく `label`（`htmlFor` / `id`）
- **必須**はラベル側で分かるように（アスタリスク等）
- 各テキスト入力・`textarea`・メール等に **記入例を示す `placeholder`** を付ける（項目名の繰り返しだけにせず、入力形式の例を日本語で示す。例: 名前「山田 太郎」、メール「example@example.com」、電話「03-1234-5678」）

### ダミー禁止

- Lorem ipsum・無意味な英文の羅列・「サンプルテキスト」のみのブロック禁止
- 未確定は短い日本語プレースホルダ（例:「（料金は要確認）」）に留める

## 4. デザイン指示書（step 5〜7 / step 4〜6）

### 配色

| 項目 | LP | CP |
|------|-----|-----|
| 配色比率 | メイン 35% / ベース 60% / アクセント 5% | メイン 25% / ベース 70% / アクセント 5% |
| CV ボタン | アクセント色 | アクセント色 |
| 遷移ボタン（CV 以外） | — | メインカラー |
| 背景 | 白・低彩度系（stone/zinc/neutral 50〜100）が既定 | 同左 |

- `design_spec` の `color_scheme` / `tokens` を最優先。仕様にない派手な色の追加・全面ベタ塗り禁止
- Tailwind 任意値 `bg-[#..]` は design_spec 定義色のみ。即興で飽和色を増やさない
- 黒文字は `#333` より濃く（`#000` 禁止）、白文字は `#FFFFFF`
- アクセントはメインの補色寄り
- **色彩バランス**: 配色は色相・明度・彩度の三属性を意識して選定する。design_spec の palette 内で明度・彩度の極端な偏りを避け、メイン・ベース・アクセント間のバランスを保つ

### 色の決め方（70:25:5 の法則）

- 基本のカラー数を 3 色にし、**ベースカラー 70% / メインカラー 25% / アクセントカラー 5%** の比率を目安とする（LP/CP 別の比率は上記表を優先）
- **メインカラー**: 明度の低い色が扱いやすい。迷ったら明度の低いものを選ぶ。発光しすぎる色は NG
- **ベースカラー**: 背景等の広い面を彩る色。白・グレー・薄い茶色等の無彩色、またはメインカラーの明度を上げた色を使う
- **アクセントカラー**: メインカラーから離れた色相にすると鮮やかになる
- **原色の直接使用禁止**: 純粋な原色（`#FF0000`, `#00FF00`, `#0000FF` 等）はそのまま使わない。少しトーンを落とした（明度・彩度を調整した）色を使用する。原色のままだと安っぽい印象になる
- **色の持つイメージを適切に利用する**: 色には心理的な印象やメッセージを伝える効果がある。ターゲットや目的に応じて選択する（例: 信頼・清潔→青、危機感・情熱→赤、自然・安心→緑、高級・神秘→紫）。色が持つイメージと矛盾する使い方をしない
- **ボタンテキストとボタン背景の明度差を確保する**: ボタンに使われるテキストは、ボタン色との明度差を十分につけて視認性を担保する。明度差が不十分で読みにくいボタンは NG
- **グラデーションは基本 2色で構成する**: グラデーションを使用する場合、3色以上の多色グラデーションは散漫になりやすいため、基本 2色で構成する

### タイポグラフィ

- 見出し以外: **PC 16〜18px / SP 12〜14px** 例外なし
- CV ボタンは本文以上のサイズ
- H1 / ヒーローキャッチ: CP は目安 40px 以上（本文の約 2 倍）
- 見出し階層を飛ばさない（h1→h2→h3）
- 長文は `max-w-prose` 相当の可読幅を確保

### フォントファミリー

- **ゴシック体を基本とする**: Noto Sans JP・メイリオなど、日常的に使われるゴシック体を選定する。イワタ新聞ゴシック等の普段見慣れないフォントは使用禁止
- **明朝体を使用する場合**: UD明朝・マティスなど日常的に使われる明朝体を選定する。花園明朝等の馴染みのないフォントは使用禁止
- **フォントウェイトのコントラスト**: タイトル・見出しは **Bold（700）**、本文は **Regular〜Medium（400〜500）** とし、タイトルと本文の太さに明確な差をつける。タイトル・本文の両方が太文字（Bold）は NG
- **letter-spacing（カーニング）**: 基本は `letter-spacing: 0`（CSS 既定値）を維持する。文字間が広すぎると文字のつながりが悪く読みづらくなるため、広げすぎない

### ヒーロー寸法

- 高さ: PC 750px / SP 550px 固定
- 必ず画像を用いる（画像なしの単色/CSS模様のみのヒーロー禁止）
- 画像上のテキストはオーバーレイで表示

### セクション間余白

- 非中間 CTA セクション: PC 100px / SP 50px
- 中間 CTA セクション: PC 50px / SP 25px
- 同一背景色の連続禁止
- CTA セクション背景は人物以外の画像＋オーバーレイ

### 装飾の禁止事項

- カード/ボックス内の絵文字・ロゴ禁止（LP は見出し〜リストへの絵文字も禁止、原稿にあるもの除く）
- 見出し下線装飾禁止
- グレースケール画像禁止
- 主要ブロックの大きな斜め配置禁止（装飾バッジ ±8° まで可）
- SP で画像過大配置禁止

### 画像の使用ルール

- **人物の顔に要素を重ねない**: 人物写真の顔部分にテキスト・図形・バッジ等を重ねない。顔は注目を集める要素であり、重ねると視認性が低下しデザインの印象が悪くなる
- **写真トーンの統一**: 複数写真を使用する場合、明度・色味・コントラストをサイト全体のトーンに揃える。1 枚だけ明度やカラートーンが異なる写真が混在するのは NG
- **人物の視線方向と要素配置**: 人物写真では視線の先にテキスト・CTA 等の主要素を配置する。視線の先に配置された要素は自然に目線が誘導され、情報が伝わりやすくなる（正面を向いている場合は除く）

### アイコンスタイルの統一

- アイコンのスタイル（線の太さ・形状・テクスチャ）や配色（同系統・同色）を揃え、全体のビジュアルの一貫性を保つ
- 同一セクション・同一ページ内で、塗りつぶしアイコンと線のみアイコンを混在させない
- フリー素材を利用する場合は、同一のイラストレーター・同一セットから選択する

### デザイン4原則

#### 近接（Proximity）

- **関連する項目をまとめてグループ化する**: 関連しない情報同士を近づけず、関連する情報を視覚的にまとめる。ページの構造と内容の直線的な手がかりをユーザーへ提供する
- **画像とテキストの距離を適切に配置し、明確なグルーピングをする**: 画像とテキストが離れすぎると関連性がユーザーに伝わらない。画像とそれに対応するテキストは近接させる
- **見出しの行間を適切に設定し、明確なグルーピングを行う**: 見出しと詳細文の間隔が広すぎると、詳細文との距離が同じになりグルーピングが曖昧になる。見出し下の余白は、見出し上の余白（前セクションとの距離）より小さくする

#### 整列（Alignment）

- **要素を意図的に整列して配置し、一体性を持たせる**: すべての項目が他の項目と視覚的に関連するよう、意図的に整列して配置する。各要素がバラバラに配置されていると散漫な印象になる
- **見出しと詳細文に見えない線を作る**: 見出しと詳細文を同じ左揃えに設定し、見えない線（視覚的な整列）を意識する。見出しが中央揃え・詳細文が左揃えのように揃え方が混在するのは NG
- **カラムレイアウトでテキスト部分は左揃えにする**: カラムレイアウトでは、テキスト部分を左揃えにすることで視覚的なまとまりと読みやすさを確保する。中央揃えはテキストの開始位置が不明瞭になり、視線の動きが不自然になるため NG

#### コントラスト（Contrast）

- **情報に優先度をつけ、違いを明確にする**: 異なる要素をはっきりと違わせること。フォントサイズの差（ジャンプ率）、文字の太さの違い、色の違いなどで情報の階層を明示する。レイアウトだけでなく、フォントサイズ・ウェイト・色のすべてでコントラストを意識する

#### 反復（Repetition）

- **特徴的な要素を繰り返すことで一貫性を持たせる**: デザイン上の特徴（角丸の半径・線種・余白スケール・カードの構造・見出しの装飾パターン等）をサイト全体を通して繰り返し、一貫性を保つ。セクションごとにバラバラのスタイルにしない

### CTA ボタン・CTA セクションの品質（全プラン共通）

- **CTA ボタンはサイト内で一番目立つデザインにする**: アクセントカラーを使用し、サイトのメインカラーと同色で埋もれないようにする。サイトカラーと同色で目立たない CTA は NG
- **CTA ボタンは塗りつぶす**: CTA ボタンに色をしっかりつけて最も目立つようにする。白背景の outline だけのボタンは NG
- **CTA ボタン内の文言は太字（`font-bold`）にする**: ボタン内テキストの視認性を高める
- **CTA ボタンと同じ形状・色のデザイン要素を他に配置しない**: ステップバッジ・ラベル等が CTA と同じ形状・色だと、CTA と誤認される。CTA は他の装飾要素と差別化する
- **電話番号もボタン形式にする**: 電話番号をテキスト表記のみにすると、クリック可能であることが不明瞭。ボタン形式にしてクリック率を上げる
- **LINE ボタンの色は LINE カラーコード `#00B900` を使用する**: LINE の公式カラーと異なる色を使うと違和感が出る

### コンテンツ表示の効率性（全プラン共通）

- **特徴の数が多い場合はコンパクトに表示する**: 特徴を大きく配置しすぎて画面が縦に伸びると、一目で全体を把握できない。情報量が多い場合はコンパクトにまとめてユーザーがスムーズに全体像を理解できるデザインにする
- **アイコンが目立ちすぎるデザインは避ける**: アイコンは情報を視覚的に補完し連想を助けるための要素。アイコンが主役になり見出しやテキストの重要性が薄れるデザインは NG。アイコンは補足情報として控えめに配置し、見出しやテキストを主役にする
- **画像+詳細テキストのレイアウトでは画像を小さく配置し、画面縦幅を抑える**: 画像が大きすぎるとメインのコンテンツ（テキスト）が埋もれる。画像は必要な情報の補完として使い、テキストを引き立てる
- **サービスの流れ: アイコンサイズを小さくし、できるだけ短い縦幅で収める**: フロー図のアイコンが大きいと画面が縦に伸び、流れ全体の把握に多くのスクロールが必要になる

### 料金表示（全プラン共通）

- **「円」「¥」は小さくする**: 金額の「円」「¥」の文字サイズを数字より小さくし控えめにすることで、価格への過剰意識を防ぎ、ユーザーが価格そのものに自然に焦点を合わせられるようにする
- **プラン・料金は枠（カード・ボーダー）で囲む**: 料金プランはテキストを枠やボックス内に配置し、強いグルーピング関係を作る。枠なしだと関連情報がバラバラに見え理解に時間がかかる

### ナビゲーション・見出しの日本語表記（全プラン共通）

- **メニューは日本語で作成する（TOP は例外）**: メニューを日本語で作成することで、訪問者にとってシンプルで分かりやすいナビゲーションを提供する。英語表記は内容が伝わりにくくなるため避ける
- **英語見出しの場合、日本語で補足をする**: 英語のみの見出し（例: "About us"）だけでは内容が伝わりにくいため、日本語のサブタイトルや補足テキストを添える
- **ボタン文言は「〇〇を詳しく見る」など具体的に記載する**: 「詳細を見る」等の曖昧な表現は避け、クリック後のアクションを明確に伝える文言にする（例: 「飲食事業を見る」「採用情報を見る」）
- **要素なのか背景（あしらい）なのかをはっきりさせる**: テキストとしての利用なのか、背景装飾としての利用なのかが曖昧なデザインは避ける。見出しは見出しとしてはっきり読めるデザインにする

### 問い合わせフォームの UX 設計（全プラン共通）

- **問い合わせ後の流れを明記する**: フォーム上部に「1 営業日以内に担当者からご連絡」等の対応フローを記載し、ユーザーに安心感を与える
- **わかりやすいプレースホルダーを設定する**: 入力すべき情報の形式が一目でわかるプレースホルダーを設定する（例: 「例: 〇〇花子」「例: 03-0000-0000」）
- **入力しやすい順序で項目を並べる**: 簡単で迷いが少ない項目（名前等）から始め、徐々に個人情報（電話番号・メールアドレス等）へ進む順序にする
- **必須項目は最小限にする**: 必須項目は「お名前」と「メールアドレス」に限定し、ユーザーに過度な負担を与えない仕様にする
- **送信ボタンは視覚的に目立つデザインにする**: 送信ボタンはアクセントカラーで大きく、押しやすいデザインにする

### LP 専用デザインルール（BASIC LP のみ）

#### LP ストーリーライン構造

LP は「**興味の引きつけ → 信頼獲得 → お得で損しない**」の 3 段階ストーリーラインで構成し、各フェーズで訪問者の態度変容（BEFORE → AFTER の心理変化）を意識する。

- **フェーズ 1 — ベネフィット「興味の引きつけ」**: まず引き込む → 心にブッ刺さる共感・悩み → 解決策を突きつける
- **フェーズ 2 — 信用を作るコンテンツ「信頼獲得」**: ベネフィットの裏付け・内容訴求 → 実績で証明する。具体的には (1) 内容の深掘り（サービスの特徴・選ばれる理由）、(2) ベネフィットの裏付け（お客様の声）、(3) 圧倒的な実績（サービス実績、よくある質問、運営者情報）を配置する
- **フェーズ 3 — オファー「お得で損しない」**: 「1,2 で積み上げた期待 > 問い合わせた際のリスク」の方程式を成立させるオファーで行動させる

#### ファーストビュー設計

- **ファーストビューは「キャッチコピー → サブテキスト → アイキャッチ画像 → CTA ボタン」の 4 要素で構成する**: この 4 要素を揃えることで、訪問者に何のサービスか・何が得られるかを瞬時に伝える
- **ファーストビューは「1（ワン）2（ツー）3（スリー）」のリズムで構成する**: 色と図形で明確な境を作り、情報を区切りながら視覚的なリズムを生み出し、ユーザーが内容を整理して理解しやすいデザインにする
- **キャッチコピーはユーザーベネフィットを訴求する**: 機能的ベネフィット（具体的なプラスの変化）と感情的ベネフィット（ポジティブな感情や心の変化）の両方を意識し、サービス名やロゴではなくユーザーが求める結果や価値を伝える

#### コンテンツルール

- **お悩みセクション: SP 画面で一画面に収めるようにする**: ユーザーが一目でお悩みの内容を把握できるように、関連情報を一画面に収める
- **お悩みの文章で特に読んでもらいたい箇所を色変更またはアンダーラインで強調する**: 特に重要な部分に視覚的な優先順位をつけ、情報の理解をスムーズにする
- **お悩みは 4 つ以上列挙する**: お悩みの情報を 4 つ以上列挙することで、ユーザーの心に響くポイントが増え、ターゲット層との共感を強化できる
- **実績・お客様の声: BEFORE-AFTER では数字の変化を視覚的に強調する**: 何を伝えるべきか（数字の変化）を明確にし、サービスの効果が直感的に伝わるデザインにする
- **実績・お客様の声: お客様氏名は黒よりも薄くし小さく記載する**: お客様の声や実績を中心に配置し、名前や役職は目立たせずで良い。名前が太文字黒で一番目立つのは NG

### CP の目的・設計指針（全 CP プラン共通）

コーポレートサイトの目的は「**企業の存在意義を語り、信頼とファンを増やすこと**」。役割は (1) お問い合わせへの誘導、(2) 求人応募への誘導、(3) 企業情報をまんべんなく伝える（理念・サービス概要・会社概要・採用情報）、(4) ブランディング（企業のイメージづくり）。

良い CP の条件:
1. 企業の存在意義が明確で、すっと理解でき、心に届く
2. 存在意義（WHY）から提供サービス（WHAT）が自然に理解される
3. 企業の雰囲気やブランドイメージが一貫して表現されたデザイン
4. 情報に迷わずたどり着けるシンプルな構成
5. 理念が共感を呼び、採用へとつながる
6. 社員の共通の目標や方向性が示されている

- **CP のストーリーラインは「存在意義(WHY) → 提供サービス・会社概要(WHAT) → 問い合わせ導線」で構成する**: WHY-HOW-WHAT のフレームワークで、すっと内容を理解でき、すぐに知りたい情報が手に入るシンプルな動線設計にする

### CP 専用デザインルール（全 CP プラン共通）

- **企業理念セクション: About + キャッチコピー + 詳細文章の順で構成する**: 最初に要点（キャッチコピー・vision/mission/value）を伝え、詳細はその後に説明することで、効果的にメッセージを伝える。重要なメッセージがどこにあるか分からない構成は NG
- **固有名詞のサービスには補足情報を加える**: サービス名（固有名詞）だけではユーザーに内容が伝わらないため、サービスの内容や特徴を詳細に補足し、一目で理解できるようにする
- **サービスの詳細文は 4 行以内にまとめる**: サービス説明の詳細文は短く簡潔にまとめる。長すぎると情報が散漫になりユーザーにストレスを与える
- **募集要項の項目名とその内容の距離を適切に取る**: 募集要項テーブルの項目名と内容の距離感が適切でないとグルーピングが弱まる。近接の原則に従い、関連する項目名と内容を近づける

### BASIC CP 専用デザインルール（単ページ CP のみ）

BASIC CP（単ページ）は以下の順序で構成する（※一例のため、必要なセクションは適宜入れること）:

- **採用あり**: メインビジュアル → 企業理念・存在意義 → 事業内容・サービス説明 → 代表挨拶・メンバー紹介 → 応募者へのメッセージ（採用情報） → 会社概要 → アクセス → お問い合わせ
- **採用なし**: メインビジュアル → 企業理念・存在意義 → 事業内容・サービス説明 → 代表挨拶・メンバー紹介 → 会社概要 → アクセス → お問い合わせ

### 複数ページ CP 専用デザインルール（STANDARD / ADVANCE のみ）

複数ページ CP の TOP ページは **WHAT 中心、HOW・WHY は小出し**にする。TOP で WHAT を見た訪問者が HOW・WHY を知りたい場合は下層ページで届ける。

TOP ページ構成（※一例のため、必要なセクションは適宜入れること）:

| 区分 | セクション | 内容 |
|------|----------|------|
| WHAT（WHY含む） | メインビジュアル | 企業理念を露出 |
| WHAT（WHY含む） | 企業理念・存在意義 | 企業理念を補足するメッセージ。スマホ1画面いっぱいに |
| WHAT | サービス動線 | サービス名+説明文（スマホ3行以内）+画像+詳細ページへの誘導ボタン。サービス名が固有名詞の場合は補足を入れる |
| WHAT | 会社概要 | 一番みられる内容なので TOP で露出。ページへの誘導ボタン |
| WHAT | 会社案内動線 | 代表挨拶など。会社案内に関連する事項を露出。ページへの誘導ボタン |
| WHAT（WHY含む） | 採用動線 | 応募者へのメッセージを述べる採用情報ページへの誘導ボタン |
| WHAT | お問い合わせ導線 | お問い合わせページへの導線 |

- **TOP ページの採用導線には、求職者に刺さるメッセージを簡潔に記載する**: TOP ページは訪問者が最初に目にする部分。採用情報ページへの動線では、曖昧な長文ではなく求職者に刺さる端的なキャッチコピーを記載する

## 5. 影・立体感・インタラクション（technical_spec + step 共通）

### 影

- カード・料金パネル等のコンテナ: `shadow-sm` / `shadow-md` または `ring-1 ring-black/5`
- `shadow-2xl` 以上の濃いドロップシャドウの乱発・ネオン風 glow・テキスト直接の影は禁止

### ホバー・アニメーション

- カード: `hover:-translate-y-0.5`〜`1` + `hover:shadow-md`（軽いリフト）
- ボタン: `active:scale-[0.98]`（押下フィードバック）
- `transition-colors` / `transition-transform` / `duration-200`〜`300`
- スクロール入場: `motion-safe:` 内で `opacity`・軽い `translate-y`・控えめな `scale`
- 複数カードの stagger: `delay-75` 段階（最大 ~300ms）

### 禁止されるアニメーション

- 自動再生・無限ループ・点滅・大バウンス・視認性を損なうパララックス過多
- `prefers-reduced-motion: reduce` で装飾的な動きを実質オフ

## 6. 実装段階（step 7-1〜7-5 / step 8-1〜8-3）

### コード構造

- STANDARD/ADVANCE: **単一ファイル・`useState` 擬似ルーティング**で全ページを内包
- LP: `app/**/page.tsx` 1 本のみ（法務はモーダル等）
- FAQ はアコーディオン必須
- CTA 行はボタン見た目
- カードの `mt-auto` で CTA 位置揃え

### 画像

- Unsplash・外部ストック URL 禁止
- ヒーローに必ず画像（`next/image` + `public/images/`）
- マニュアル段はプレースホルダ可。最終リファクタ（Manus）で置換
- `Image` の `src` は `/images/...`（`/public/` を含めない）
- `width` + `height` を数値で渡すか `fill` + 親に `relative`
- 非ヒーロー画像プレースホルダは SP 縦 300px 未満

### 下層ページヒーロー（STANDARD/ADVANCE）

- 全ビューに `ImagePlaceholder` 等
- 紺ベタ＋テキストのみの SubPageHeader 禁止
- `absolute inset-0` + 暗オーバーレイ + 前面見出し
- 共通 `SubHero` なら `props` で背景差し替え

### 日本語折り返し

```css
h1, h2, h3, h4, h5, h6 { text-wrap: balance; word-break: auto-phrase; }
p, li { text-wrap: pretty; word-break: auto-phrase; }
```

- `word-break: break-all` 禁止（日本語で不自然な切断）
- `white-space: nowrap` を h1〜h6・p・li に適用しない（SP オーバーフロー原因）
- 折り返し位置調整に素の `<br />` 挿入禁止（SP/PC 分けは `className` で制御）

### アイコン

- 基本: Lucide React（実在する名前のみ import）
- SNS: Simple Icons（`react-icons/si`）
- アイコンを画像プレースホルダで代用しない

### UX・アクセシビリティ

- タップ領域: 主要なリンク・ボタンは `min-h-[44px] min-w-[44px]` 目安
- フォーカス: `focus-visible:outline` でフォーカスリングを消さない
- ランドマーク: `<main>` を各ページに 1 つ、`nav` に `aria-label`
- モバイルで横スクロールを起こさない

### CTA・視覚的階層

- 1 ビューあたり primary CTA は 1 系統。副次は `outline` / `ghost`
- 虹色の複数 primary 禁止
- 同一文言のボタンを短いスクロール内に何度も並べない

### パフォーマンス

- ヒーロー等 LCP 画像に `priority` 付与
- 装飾・下層の画像は遅延読み込み、`sizes` を適切に指定

## 7. 絵文字の絶対禁止（全工程 Override 禁止）

- Unicode 絵文字を見出し・本文・リスト・表・ボタン・FAQ・フォーム・ナビに含めない
- `aria-label`・`alt`・`title`・コミットメッセージにも装飾用絵文字を入れない
- 例外: ヒアリング原稿に明示的に含まれる絵文字のみそのまま転記可
- 代替: タイポ階層・余白・配色・Lucide アイコンで強調

## 8. Manus リファクタ工程のルール

### コンテンツ量の完全維持（最重要）

リファクタリングは「コードの構造変換」であり「内容の編集・要約」ではない。

- 元ソースの全テキストを一字一句変更・省略・要約しない
- 表の行数・FAQ 数・カード枚数・リスト項目数を減らさない
- 料金・住所・メール等の具体的な数値・固有名詞をすべて残す
- 元コードのテキストを「そのままコピー」（自分の言葉で書き直さない）

### レイアウト構造の完全維持

- セクションのレイアウトパターン（全幅背景/2カラム/カード列/中央揃え）を変更しない
- 背景画像+オーバーレイ構造を CSS グラデーションに差し替えない
- 固定高さ（`h-[550px]` 等）を padding ベースに縮小しない
- コンポーネントの props をリネーム・削除しない
- グリッド列数・カラム比率を変更しない

### 配色の完全維持

- 元コードの `bg-[#...]` / `text-[#...]` のカラーコードを 1 つも変更しない
- テンプレートのデフォルト（白背景）で元コードの配色を上書きしない

### page.tsx のルール

- `app/**/page.tsx` 内に className・レイアウト要素を書かない（import + コンポーネント列のみ）
- 全 JSX は `app/components/` に移す

### 画像生成（nanobananaPro）

- 人物は必ず「日本人（Japanese）」を指定
- 画像に文字を含めない
- 保存先: `/public/images/`
- 背景画像は元コードと同じ CSS 手法で差し替え（サイド配置に変更禁止）
- 全プレースホルダを置換（残存禁止）
- 全生成画像がコードから参照されていること

### CSS・Hydration

- globals.css: 原則空。元コード `<style>` の移植 + 日本語折り返し CSS + アニメーション JS 接続のみ
- `<p>` 内に block 要素禁止
- `body` に `suppressHydrationWarning`
- `window` / `document` は `useEffect` 内
- Tailwind v4 時は `@theme` にトークン定義

### ビルド検証

- `npm run build` が通る状態がゴール
- エラー時は人間に聞かずログを読み、自己修復
- ページ数が契約と完全一致（自動チェック）

## ルールの改善方法

品質問題を発見した場合:

1. `output/<レコード番号>/llm_steps/` で**問題が発生したステップを特定**
2. `input.md`（プロンプト）と `output.md`（応答）を比較し、プロンプトの不足か LLM の傾向かを判断
3. **全プラン共通の問題** → `config/prompts/common/technical_spec_prompt_block.txt` にルール追加
4. **特定ステップの問題** → `config/prompts/*_manual/step_*.txt` を編集
5. **リファクタの問題** → `config/prompts/manus/orchestration_prompt.txt` または `refactoring_instruction_handwork.txt` を編集
6. **工程スナップショット**（`scripts/phase2_from_phase1_snapshot.py`）で同じ入力に対して改善効果を検証
7. 本書（`TECH_REQUIREMENTS.md`）を更新して索引を最新に保つ
