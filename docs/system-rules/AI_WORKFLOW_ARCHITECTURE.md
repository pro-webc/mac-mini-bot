# AI ワークフローシステム アーキテクチャ

## このドキュメントの目的

mac-mini-bot は**半 AI ワークフローシステム**であり、最終的には**自律的な AI ワークフローシステム**を目指している。本ドキュメントは、現在のシステム全体像を「AI ワークフロー」の観点で定義し、**誰（何）がどの判断を担っているか**の境界を明文化する。

---

## システムの全体構造

```
┌──────────────────────────────────────────────────┐
│  AI オーケストレーション層（現在: 人間 + Cursor）    │
│                                                    │
│  ・案件の状況判断・優先順位                          │
│  ・障害診断 → 再開スクリプト選択                     │
│  ・プロンプト改善サイクルの実行                       │
│  ・新プラン分岐の設計・実装                          │
│  ・コードの修正・テスト・デプロイ                     │
│                                                    │
│  判断基準: .cursor/rules/ + docs/ + 暗黙知          │
└────────────────────┬─────────────────────────────┘
                     │ 起動・設定・再開コマンド
                     ▼
┌──────────────────────────────────────────────────┐
│  実行エンジン（mac-mini-bot: main.py）              │
│                                                    │
│  Phase 1: ヒアリング抽出 + 作業分岐決定              │
│  Phase 2: Claude CLI 多段チェーン（+ Manus）         │
│  Phase 3: サイト組立（clone or フェンス適用）         │
│  Phase 4: npm run build（自己修復ループ）            │
│  Phase 5: GitHub push → Vercel デプロイ             │
│                                                    │
│  記録: output/<record>/llm_steps/（全入出力トレース）│
└────────────────────┬─────────────────────────────┘
                     │ API 呼び出し
                     ▼
┌──────────────────────────────────────────────────┐
│  外部 AI / サービス                                 │
│                                                    │
│  ・Claude Code CLI（テキスト / コード生成）           │
│  ・Manus API（リファクタ / 画像生成 / push）         │
│  ・Google Sheets API / GitHub API / Vercel API      │
└──────────────────────────────────────────────────┘
```

## 3 層の役割分担

### 1. AI オーケストレーション層（人間 + Cursor エージェント）

**現在の担い手**: プロジェクトオーナー + Cursor IDE のエージェントモード

| 責任 | 具体例 |
|------|--------|
| **計画** | どの案件をいつ処理するか、どの順で進めるか |
| **判断** | エラー発生時にどの再開スクリプトを使うか、プロンプトをどう改善するか |
| **修正** | コードのバグ修正、新プラン対応、テスト追加 |
| **評価** | 生成サイトの品質レビュー、LLM 出力の検査 |
| **改善** | `config/prompts/*.txt` の編集、`COMMON_TECHNICAL_SPEC` の更新 |

**判断に使う情報源:**
- `output/<record>/llm_steps/` — 各ステップの入出力
- ログファイル — フェーズの進行とエラー
- スプレッドシート — 案件ステータスと結果 URL
- `.cursor/rules/` — 判断の標準手順（後述）

### 2. 実行エンジン（mac-mini-bot）

**担い手**: `main.py` の `WebsiteBot`

| 責任 | 具体例 |
|------|--------|
| **キュー管理** | スプレッドシートから条件に合う案件を取得 |
| **パイプライン実行** | 5 フェーズを順に実行。分岐は `BRANCH_REGISTRY` で静的に決定 |
| **トレース記録** | 全 LLM 入出力を `llm_steps/` に自動保存 |
| **自己修復** | `npm run build` 失敗時の再試行ループ（Phase 4 限定） |
| **ステータス更新** | スプレッドシートの AI ステータス列・URL 列の書き込み |

**できないこと（= オーケストレーション層に委ねていること）:**
- Phase 2 途中で止まった場合の再開判断
- プロンプト品質の評価・改善
- 新しいプランへの対応
- 予期しないエラーの根本原因分析

### 3. 外部 AI / サービス

| サービス | 役割 | 制御する設定 |
|----------|------|-------------|
| Claude Code CLI | テキスト / コード生成（多段チェーンの各ステップ） | `CLAUDE_*_MODEL`, `CLAUDE_CLI_TIMEOUT_SEC` |
| Manus API | リファクタ / 画像生成 / GitHub push | `MANUS_*` 系環境変数 |
| Google Sheets API | 案件キュー / ステータス管理 | `GOOGLE_SHEETS_*` |
| GitHub API | リポジトリ作成 / push | `GITHUB_TOKEN`, `GITHUB_USERNAME` |
| Vercel API | デプロイ / 公開 | `VERCEL_*` |

## `.cursor/rules/` の位置づけ

`.cursor/rules/` は **AI オーケストレーション層の判断基準をコード化したもの**。Cursor エージェントがコードを変更する際に自動的に適用される。

| ルール | 何を制御するか | なぜ必要か |
|--------|--------------|-----------|
| `log-reading-discipline.mdc` | **障害診断の手順** — ログを読まずに推測しない、設定変更の前に因果を確認 | 誤診断による無駄な設定変更を防ぐ |
| `parallel-branch-fixes.mdc` | **横展開の義務** — 1 つの分岐を直したら同種の分岐も確認して揃える | 4 つの `*_claude_manual.py` の不整合を防ぐ |
| `comment-conventions.mdc` | **コメント規約** — パイプライン境界では引数・処理・出力を書く | 次にコードを読む AI / 人間の理解速度を維持 |
| `solid-yagni.mdc` | **設計原則** — 今の要件に不要な機能は追加しない | 過剰な抽象化とデッドコードの蓄積を防ぐ |

**将来の AI 層への移行で重要な点**: これらのルールは、将来 AI が自律的に判断する際の**知識ベースの原型**である。ルールの内容を増やし体系化することで、人間 + Cursor の暗黙知をシステムに移転できる。

## トレーサビリティの設計

AI ワークフローシステムとして最も重要な基盤は**全 LLM 入出力の記録**。

```
output/<record>/
├── llm_steps/                          ← 第 1 層: ステップトレース
│   ├── 001_claude_cli_generate/
│   │   ├── input.md                    ← LLM に送ったプロンプト
│   │   └── output.md                   ← LLM の応答
│   ├── 002_claude_cli_chat/
│   └── ...
├── llm_raw_output/                     ← 第 2 層: 加工前の正本
│   ├── spec.yaml
│   └── requirements_result.yaml
└── sites/<name>/llm_raw_output/        ← 第 3 層: サイト側の記録
```

**この記録が可能にすること:**
- プロンプト改善の A/B 比較（同じ入力で異なるプロンプトの出力を比較）
- 障害の根本原因特定（どのステップで品質が落ちたかを遡及）
- 将来の AI 自律評価ループ（出力を自動評価 → プロンプトを自動調整）

## 現在の自動化境界と将来の進化

| 機能 | 現在 | 将来（AI 自律化） |
|------|------|------------------|
| 案件キュー取得 | bot が自動取得 | 変更なし |
| 作業分岐の決定 | `BRANCH_REGISTRY` で静的ルール | AI がコンテキストから動的に判断 |
| Claude 多段チェーン | bot が固定ステップ順に実行 | AI がステップを動的に構成・スキップ |
| 品質評価 | 人間がレビュー | AI が出力を自動評価しフィードバック |
| 障害対応 | 人間 + Cursor で診断 → 再開スクリプト | AI が自律的に診断 → 再開 |
| プロンプト改善 | 人間が `llm_steps/` を見て手動で編集 | AI がトレースから改善案を生成 |

**現段階で焦らないこと**: 宣言的ワークフロー定義やプラグインアーキテクチャは、AI 層の要件が具体化してから導入する（YAGNI）。現在はトレース基盤とルールの蓄積が優先。

> **次のステップ**: 自律化に向けた具体的な計画は [EVOLUTION_ROADMAP.md](./EVOLUTION_ROADMAP.md) を参照。Phase A（自動スコアリング）から段階的に進める。
